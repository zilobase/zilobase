# Automation execution lifecycle

[Run engine](../../../apps/server/src/features/automations/execution/run-engine.ts) exposes the existing drain and single-delivery interface. [Run claims](../../../apps/server/src/features/automations/execution/run-claims.ts) owns database-clock claim selection, sorted workspace advisory locks, concurrency slots and lease renewal. [Run lifecycle](../../../apps/server/src/features/automations/execution/run-lifecycle.ts) owns the heartbeat, access/lock checks, restored execution state and terminal run/automation updates. [Execution context](../../../apps/server/src/features/automations/execution/execution-context.ts) loads the pinned revision and resources; [action executor](../../../apps/server/src/features/automations/execution/action-executor.ts) selects the concrete action implementation.

[Run steps](../../../apps/server/src/features/automations/execution/run-step.ts) owns receipt acquisition, action execution, step output/failure persistence and durable retry dispatch. Step receipts use a stable run/action identity. A succeeded receipt can restore the output rather than repeat the action. Retrying work retains its revision and idempotency identity. Updating a definition after a run is queued must not change that run's instructions.

Internal mutations recheck data-source access and preserve automation origin. External Gmail, Slack and webhook actions have distinct connection ownership, credential and retry behavior. Webhooks use pinned egress; [the runbook](../../../docs/databases/automation-operations-runbook.md) and [threat model](../../../docs/databases/automation-threat-model.md) describe operations and security constraints.

A lost lease must not let an old worker complete another worker's claim. Terminal failure updates run and automation state; skipped work differs from failed work. Preserve scheduled occurrence context, workspace concurrency and step receipts when changing implementation shape.

[Lifecycle tests](../../../apps/server/src/features/automations/execution/run-lifecycle.test.ts) exercise the public drain interface with controlled database and provider adapters. They cover duplicate delivery without a claim, expired-lease recovery, completed-output restoration, failed-receipt reuse, heartbeat renewal/cleanup, lease loss during an action, retryable and terminal provider failures, revoked access and workspace capacity. Retry persistence still precedes dispatch; the lease is asserted before receipt acquisition, before the action and before writing its result.

[Execution-context tests](../../../apps/server/src/features/automations/execution/execution-context.test.ts) exercise pinned-definition parsing and the generated revision/worker predicates, including a newer current revision, invalid pinned content and missing scheduled occurrences. These tests ran against the original engine before the split. Structural assertions for the now-covered pinned revision and step identity were removed; [remaining source assertions](../../../apps/server/src/features/automations/execution/run-engine-architecture.test.ts) protect composition and provider-specific safeguards. Controlled tests do not establish concurrent PostgreSQL locking behavior or real provider delivery. No live provider action is part of refactor verification.
